# Structured file tools within Target Folders

The subsequent decision in [ADR 0004](./0004-command-tool-isolation-boundary.md) replaces the fixed seven-tool interface, execution implementation and Target-Folders-only authorization with Codex exec-server and shared file/command permissions. The replacement is delivered by #146/#147 as `exec_command`, native byte-bounded `read_file`, built-in `apply_patch` and `read_tool_output`. The original decision below records the previous implementation; its specific tool contracts are not compatibility requirements for the replacement. Saved historical Tool Calls remain inspectable.

Replace the example file counter with seven structured tools: `list_files`, `search_files`, `read_file`, `write_file`, `edit_file`, `move_path` and `delete_path`. Each Tool Call performs one operation with an independent result; repeated calls retain their identities and execute serially within the existing Agent loop, avoiding shell access and multi-path batch variants. The discovery/read trio is delivered in #125 and mutations in #126.

Project Target Folders, read anew before each call, are the only application-level filesystem authorization rule. Resolve containment for existing paths and destinations through existing parents; reject traversal, sibling-prefix tricks and out-of-scope content access, and do not recursively follow links outside scope. Hidden paths and `.git` are permitted within scope, with no Git requirement, clean/tracked checks, `.git` guards or Git recovery promise; OS permissions still apply. Mutation prerequisites are checked before changing files, errors and cancellation report actual effects without a rollback claim, and generic Tool Call history/redaction remain unchanged.

All selected Target Folders form one authorized scope. A resolved target is in scope when it lies within any selected folder; it need not lie in the same selected folder as the symbolic link.

For entry operations, when the final path entry passed to `delete_path` or `move_path` is a symbolic link, delete or move that link itself. The referenced file or directory must remain unchanged. Authorize the affected link entry and move destination; a dangling or out-of-scope referenced target does not prevent operating on an otherwise in-scope link. Moves preserve the stored link target and normal rename semantics, even when a relative link resolves differently at its destination. Resolving parent directories must not turn a link operation into a mutation of its target.

Content tools (`read_file`, `write_file` and `edit_file`) follow symbolic links when the resolved target lies within any selected Target Folder, including a different selected folder from the link. Writes and edits intentionally modify that target while preserving the link. Apply the same target containment rule when a parent directory is a symbolic link; do not reject authorized content access merely because its path uses a link. Targets outside the project's combined scope remain inaccessible.

Reads/searches/edits/writes support UTF-8 text; listing/moving/deleting also support other files. Bound listing/search to 100 results with offset continuation and reading to 2,000 lines or 50 KiB with line/column continuation. Use relative-path Node `path.matchesGlob` discovery patterns and literal case-sensitive content queries; fixed bounds and one exact, uniquely matching edit keep the interface small without adding dependencies or configurable modes. File/folder moves reject destination collisions; writes create missing scoped parents, and directory deletion is recursive. Verification uses existing HTTP/model-loop fixtures, temporary folders/databases and fake models, checks actual filesystem effects/results and continuation, and retains the generic Chromium Tool Call coverage without paid requests or development database deletion in either file-tool slice.

Mutation results report paths and bytes written or deletion, without echoing whole content. Unsupported replacement text (NUL or unpaired surrogate) is rejected. Edits reject empty or ambiguous oldText, including overlapping occurrences. Move destinations require an existing parent and reject existing entries, including dangling symlinks. Cancellation or filesystem failure after mutation begins reports mutationMayHaveOccurred; operations are not transactional and have no rollback promise.

Concurrent service mutations reserve their resolved destination and reject a competing operation immediately; there is no queue. The reservation does not coordinate with other processes. Node rename provides no atomic no-replace flag, so external filesystem changes between prerequisite validation and mutation remain an OS concurrency limitation.

Reads and searches use the shared fatal streaming UTF-8 decoder and retain only bounded pages, query overlap, excerpt windows and location counters. A full page does not stop selected-file validation: a later NUL or invalid UTF-8 makes read fail or search discard every match from that file. Unicode code-point continuation, literal first-match columns, offsets, BOM/newline content and cancellation are preserved without file-size or line-length limits. This bounds file-scanning memory, not mutation-tool memory. The reproduced pre-repair 20-MiB single-line read returned 50 KiB while RSS grew roughly from 78 to 305 MiB; search shared the accumulating source pattern but was not independently measured in that reproduction. Isolated-process regression checks compare scan-memory growth across file sizes and exercise both read and search.
